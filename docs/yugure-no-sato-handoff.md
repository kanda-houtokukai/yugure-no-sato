## 検証の回し方（Code は毎回これを使う）

```
npm run verify                  # 5視点（front/bird/ground/water/walk）＋太陽ずらし1枚。異常があれば終了コード非0
node tools/shot.mjs 'view=front&dbg=1'   # 1視点だけ撮って数値を出す（試行錯誤用）。dbg: 1法線 2材質 3高さ 4フラグメント省略 9水面塗り
npm run typecheck               # src 配下の型検査
npm run probe                   # WebGPU の取得可否を再実証（環境が変わったとき）
```

- 出力は `.screenshots/`（gitignore 済み）。`<日時>-<視点>.png`（**2560×1440**、Retina 相当）と `report-<日時>.json`。verify は各スクショの sha256 を出す。
- **撮った絵は必ず自分で Read して目視判定する。** レポートの ○ だけで終わらせない
  （輝度と分散が正常でも、絵が意図と違うことはある）。
- ゴールデンビューは**バイト単位で再現する**（実測で確認済み）。
  スクショの sha256 が前回と変われば、描画が変わったということ。回帰検出に使える。各段階の値は経緯アーカイブに記録。
- **`mode` の既定は実操作（play）**。検証は `?mode=scene` を明示する（verify.mjs / shot.mjs は自動で付ける）。
- URL パラメータで視点を上書きできる: `eye=x,z,above` `yaw` `pitch` `fov` `t` `sunAz` `sunEl` `exposure` `dbg` `frames` `script` `dpr`。
  `probe=x,z;x,z` で変形の場の値（沈み・倒れ・濁り・波紋）をレポートに載せる。
- **性能を比べるときは同一セッション内で交互に測る**。時刻が違う測定値どうしを比べない（同じコードで 2 倍動く）。
- **シェーダを変えた直後の 1 回目は GPU 時間が 30〜40ms と出ることがある**（コンパイル直後の一過性）。
  2 回目以降の値で判断する。

## 生きている注意事項

- ⚠️ **素材ファイルを1つでも入れたら実験として失格。** テクスチャ・3Dモデル・画像・音源すべて。
  判定は `git ls-files` にそれらの拡張子が現れないこと。
- ⚠️ **描画ライブラリ禁止。** `dependencies` は原則空。`devDependencies` は vite / typescript / 型定義と、
  自己修正ループに必要な最小限のみ。増やしたくなったら**停止して報告**。
- ⚠️ **仕様に無い選択を迫られたら、実装せず報告して停止する。** 勝手に決めない。
- ⚠️ **区切りごとに push して SHA を報告する。** 設計側は raw で裏取りするため、
  push 済みでないものは存在しないものとして扱われる。
- ⚠️ **public を維持する。** private 化すると設計側の裏取り手段が消える。
- ✅ **解消済み（2026-09-06）**: Chrome 152 安定版で WebGPU が取れることを機械確認した。
  **Canary は不要**（下記「WebGPU 環境」）。
- ⚠️ **`hidden` 属性に頼る要素へ、作者スタイルで `display` を書かない**（`[hidden]{display:none!important}` を置いてある）。
- ⚠️ **ポインタロックは環境によって失敗する**（Playwright 経由では必ず）。視線操作はドラッグを主に保つ。
- ⚠️ **`npm install` はグローバル設定の deny で止まる**（`~/.claude/settings.json` の `Bash(npm install*)`）。
  これは意図的なガード。Code が勝手に外さず、**神田さんに自分のターミナルで実行してもらう運用**とする
  （2026-09-06 に本人が選択）。依存を足す必要が出たら、コマンドを提示して待つ。
- ⚠️ **`@types/node` を入れない。** devDependencies を vite / typescript / @webgpu/types の3点に保つため、
  `vite.config.ts` は `tsconfig.json` の型検査対象から外してある（`include: ["src"]`）。
  Vite は設定ファイルを実行時にトランスパイルするだけなので実害はないが、
  **`vite.config.ts` の型は機械保証の外**である点は把握しておくこと。

- ⚠️ **sink は本文の無い 204 を返してはいけない。** 書き込みが成功していても Chrome が
  `net::ERR_ABORTED` を出し、verify が偽の異常を報告する。必ず本文つきの 200 を返す。
- ⚠️ **favicon はファイルを置かず `<link rel="icon" href="data:,">` で要求ごと消す**（素材ゼロの原則）。
  無いと `/favicon.ico` の 404 が verify を汚す。
- ⚠️ **Playwright は `channel: 'chrome'` で実機の Chrome 安定版を起動する。** 同梱 Chromium は入れていない
  （`PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` でインストール）。probe で実証した動作条件をそのまま引き継ぐため。
- ⚠️ **スクショは `window.__yugure.firstFrameDone` → `sceneDone` を待ってから撮る。**
  WebGPU の初期化は非同期で、待たずに撮ると真っ黒が写る。

- ⚠️ **数式（`world.wgsl`）は唯一の正本。TS に複製しない。** CPU が要る値は `runQuery`（compute）で読み戻す。
- ⚠️ **近景段（0.25m / 半径 256m）は歩き手に追従して焼き直される。** 焼き先は「使っていない方の層」で、
  焼き終えてから段 0 の原点と層を一度に差し替える（原子的）。焼き直しは 16 帯に分けて散らす。
  原点は 0.25m 格子に丸めるのでテクセル中心が一致し、**入れ替えの前後で高さは厳密に一致する**（実測 0m）。
- ⚠️ **読み戻しの `mapAsync` は encoder を submit した「あと」に始める。** 同一フレームで始めると
  「map 中のバッファを submit で使った」の検証エラーになる（errorScope が捕まえた）。
- ⚠️ **斜面を通る道は「切土・盛土の段」で作る。** 土手（周囲より高い断面）にすると 20° の斜面では
  片側が宙に浮き反対側が山に埋まる。路面の高さは両端の高さから道のりに比例させる（一定勾配）。
  近くの地面から取ると地形の形をなぞって道が波打つ。
- ⚠️ **高度 3.5° の西日では、材質の値より「面がどちらを向いているか」が効く。**
  畝を東西に立てたら両斜面とも日陰になり、albedo を 3 倍にしても黒い帯のままだった。
  南北に立て直したら西面が夕日を受けて形が読めた。**暗い＝値が低い、と決めつける前に向きを疑う。**
- ⚠️ **WGSL の `select(a, b, cond)` は a と b の両方を評価する。** 重い関数を `select` の枝に置くと、
  条件に関係なく毎画素で走る。`dbg` のような**一様な値の分岐は必ず `if` で書く**
  （計測用の `sampleNormal` と `terrainShadow` がこれで全画素・全フレーム走っており、全視点で 7〜12ms を捨てていた）。
- ⚠️ **数式を画素ごとに複数回評価しない。** 3 回で GPU の占有率が崖を越え 30〜77ms（実測）。
  高さ・法線・日向・畦距離は起動時にテクスチャへ焼き、画素側は 1 タップで読む。
- ⚠️ **太陽を動かす運用にするなら、空 LUT・法線/日向/畦距離テクスチャの焼き直しが要る**（合計 ≈100ms）。
- ⚠️ **座標系は実地図の鏡像**（北を向くと東が左）。内部では一貫しており検証も通る。実地図と比べる用途が出るまで触らない。
- ⚠️ `float32-filterable` 機能に依存（r32float の線形補間）。この Mac では利用可。
- 📋 **未検証**: 実機 Chrome で 60fps が出るかは、GPU 時間 12ms から推定しているだけ。画面付き実行での実測は
  操作を入れるフェーズ3で行う。

## WebGPU 環境（確定・2026-09-06 実測）

`node tools/probe.mjs` による実測。**Chrome の起動条件4通りすべてで WebGPU が取れた。**

| 起動条件 | 結果 |
|---|---|
| headed（フラグなし） | ✅ |
| headed + `--enable-unsafe-webgpu` | ✅ |
| **`--headless=new`（フラグなし）** | ✅ |
| `--headless=new` + `--enable-unsafe-webgpu` + `--use-angle=metal` | ✅ |

- **特別な起動フラグは不要。** `--enable-unsafe-webgpu` も `--use-angle=metal` も要らない。
- **ヘッドレスでも WebGPU が動く。** パートAで想定していた「ヘッドレスでは動かない」懸念は外れた。
- アダプタ: `vendor: apple` / `architecture: metal-3` / subgroup サイズ 32 固定
- `preferredCanvasFormat: bgra8unorm`
- 主要な上限値: `maxBufferSize` **4,294,967,292**（約4GiB）／`maxStorageBufferBindingSize` 同値／
  `maxComputeWorkgroupSizeX,Y` 1024・`Z` 64／`maxComputeInvocationsPerWorkgroup` 1024／
  `maxComputeWorkgroupsPerDimension` 65,535／`maxComputeWorkgroupStorageSize` 32,768／
  `maxTextureDimension2D` 16,384／`maxStorageBuffersPerShaderStage` 10／`maxColorAttachments` 8
- 使える主な機能: `shader-f16`・`subgroups`（size-control 付き）・`timestamp-query`・`float32-filterable`・
  `float32-blendable`・`dual-source-blending`・`depth-clip-control`・`bgra8unorm-storage`・
  `primitive-index`・`clip-distances`
- 全文は `.screenshots/probe-attempts.json`（gitignore 済み）。再取得は `node tools/probe.mjs`。

### 段階1: 歩ける範囲の拡張（`1894203`）

歩ける範囲を縛っていたのは地形の数式ではなく、**近景の高さテクスチャ**（2048²×0.25m = ±256m）だった。
中景（±1638m）と遠景（±13km）は既に足りていたので、近景段だけを歩き手に追従させた。

- 高さ・光・材質のテクスチャを 4 層にし、層 0 と層 3 を近景段の交互の置き場にした。
  焼き先はいつも「使っていない方の層」で、焼き終えてから hmLevels の段 0（原点と層）を
  **一度に差し替える**。こうすると焼いている間も絵が壊れない
- 焼き直しは 16 帯に分けて 16 フレームに散らす。1 フレームでやると 50ms 級の飛びになる。
  法線・材質は高さより 1 帯遅らせる（帯の境で法線が欠けないように）
- 中心から 160m 離れたら焼き直しを始める（半径 256m のうち 96m を余裕に残す）
- CPU 側（足元の高さ・水の判定）も新しい近景段に入れ替える

★ **教訓: 読み戻しの `mapAsync` は encoder を submit した「あと」に始める。**
同一フレームで始めると「map 中のバッファを submit で使った」の検証エラーになる（errorScope が捕まえた）。

★ **教訓: 段の原点を同じ格子に丸めれば、入れ替えは原理的に連続になる。**
`Math.floor(x/texel)*texel` で丸めるとテクセル中心が一致するので、新旧の近景段は同じ点で同じ値を返す。
実測: 5 回の焼き直しで、入れ替えの瞬間に新旧が返す高さの差は 320 点すべて **0m**。

**実測（1000m を走破）**

| 出発点からの距離 | GPU 平均 | 焼き直し | 接地中の足と地面の差 |
|---|---|---|---|
| 250m | 10.65 ms | 0 回 | 0.000000 m |
| 500m | 7.77 ms | 2 回 | 0.000000 m |
| 750m | 7.87 ms | 4 回 | 0.000000 m |
| 1000m | 8.13 ms | 5 回 | 0.000000 m |

足元の地面の 1 フレーム変化の最大は 0.2142m だったが、**焼き直しの閾値を 160m→110m に変えても
同じ時刻・同じ値**だったので、焼き直しの飛びではなく地形（社の丘の急斜面）と切り分けた。

**基準の更新**: ゴールデンビューの sha256 が front/bird/ground/water で変わった。
画素差を機械確認したところ **最大 1/255・差 2 超の画素は 0.0%**（walk は byte 一致）。
参照の書き換えによる浮動小数の丸めだけの違いなので、新しい値を基準に置き換えた。

また、runner のループ見張りが 90 秒固定で長い筋書きを途中で切っていたので、
フレーム数に応じて伸ばすようにした（60fps で描く時間の 3 倍）。

### 段階2-1: 峠道と見晴らし場（`feedd5f`）

丘は t=0.95→3.6 で 70m と勾配 9° しかなく、そのままでは折り返す理由が生まれない。
**鞍部のある尾根**（`passRidge`）を足して斜面を 20° 級にし、九十九折りを必然にした。
実測: 鞍部（u=210）60.8m に対し稜線は u=0 で 101.1m、u=320 で 92.8m。

★ **教訓: 斜面を通る道は「切土・盛土の段」で作る。**
土手（周囲より高い断面）にすると 20° の斜面では片側が宙に浮き、反対側が山に埋まる
（フェーズ5の石段と同じ罠）。幅の方向に水平にならせば、埋まりも浮きも原理的に起きない。

## 2026-09-07 — 割り込み: 集落が田の中に沈んで見える件（完了）

**実機の所見（神田さん）**: 「集落が田んぼの中にあるように感じる。あぜ道の下にある感じ」

### 原因（推測でなく実装を読んで確認）
`world.wgsl` の道の断面が場所によらず土手だった。`let pathBase = max(mix(floorH, site.level, site.w), h);`
により、敷地の中でも道の天端が地面より約 0.55m 高い。主道が集落を貫く堤防になり、家がその下に沈んで見えていた。

### 直したこと
1. **道の断面を場所で変える**: `let riseScale = 1.0 - site.w * 0.94;`。田の間は土手のまま、敷地・境内の中は
   地面と同面。`site.w` は敷地の縁で滑らかに 0→1 になるので、移行も自動的に滑らかになる。
   土手の法面を草にする判定も `site.w < 0.45` で敷地の中では作らない。
2. **敷地の地面を乾いた踏み固めた土に**: `YARD_FEATHER` 13.0 → 7.5（段差 0.85m を読ませる）、
   敷地の albedo を一段明るく。`grass.wgsl` の敷地の草を `1 - flatSite(...).w` で縁だけにした
   （人が踏む中央は生えない）。
3. **境界に石垣を並べた**: フェーズ5の石垣 8 本は敷地の**内側**に散っていて、縁に1本も無かった。
   南の縁に 5・東の縁に 2・西の縁に 1 を追加（既存テンプレート `wall10` の配置のみ。建物は触っていない）。

- 足あと: 敷地の中でも沈みが残る（walk の絵に窪みが写る）。敷地の土の沈みは `materialResponse` の

### ★ 教訓: WGSL の `select` は両辺を評価する — 計測用のコードが本番を食っていた
道を同面にしたら walk 視点が **12.8 → 18.6ms** に悪化した。交互 A/B（3往復）で `world.wgsl` が原因と
特定し、さらに `dbg` の切替で切り分けたが、稲・草・石垣・焼いた参照・変形の勾配・細部・遮蔽・遠景の


影の行進は歩数が地形の高さに依存するので、道を下げた分だけ重くなり、症状が「道の変更のせい」に見えていた。

**`ground` / `water` / `walk` の sha256 は修正の前後で完全一致**（`2c6639b4…` / `e48347c9…` / `1ccf122b…`）。
画素を1つも変えずに速くなったことの機械的な証明。フェーズ4から繰り越していた「bird 17.7ms」もこれで消えた。

## 2026-09-07 — 割り込み: 実操作が有効にならない件（完了・commit 済み）

実機で「クリックしてもポインタロックに入らず操作できない」との報告。フェーズ4に進む前に解決した。

**原因（観測で確定。推測で直していない）**
1. **主因: 既定が計測モードだった。** `npm run dev` で開く素の URL（パラメータなし）は `mode=scene` と判定され、
   120 フレームの計測が走って終わるだけ。実操作のコードは 1 行も動いていなかった。
   計装して実測: クリック時の `requestPointerLock` 呼び出しは **0 回**（ハンドラ自体が存在しない）。
2. **ポインタロックは環境によって失敗する。** `?mode=play` を付けても
   `WrongDocumentError: The root document of this element is not valid for pointer lock.` ＋ `pointerlockerror`。
   Playwright 経由の Chrome では必ず失敗する。実機の手動 Chrome でも失敗しうる前提で組み直した。

**直した内容**
- **既定を実操作モードにした**（`mode` 未指定 = play）。検証系は `mode=scene` を明示（verify.mjs / shot.mjs）。
- **視線は 3 経路**: ①ドラッグ（押したまま動かす。主。どの環境でも通る）②ポインタロック（通る環境でだけ。
  失敗しても黙ってドラッグへ落ちる）③矢印キー。ドラッグの差分は `clientX/Y` の差を主にする
  （`movementX` は合成イベントで 0 になる環境がある。実測）。
- **初見向けの案内**を開いた直後に全画面で出し、操作を始めると 420ms でフェードして消える。
  WASD を知らない前提の文言。操作中は隅に 1 行のヒントのみ。**数値 HUD は既定で非表示**（H で切り替え）。
- キャンバスは実操作では画面いっぱい（起動時の縦横比を保って収める）。描画解像度は起動時に固定。

**★教訓（いずれも実測で確定）**
- **作者スタイルで `display` を指定すると `hidden` 属性が効かなくなる。** 案内に `display: grid` を書いたため
  `[hidden]{display:none}`（UA スタイル）が上書きされ、**検証スクショに案内が写り込んで全視点のハッシュが変わった**。
  `[hidden] { display: none !important; }` を置いて解決。画像を 1 画素ずつ差分して「100% の画素が違う・左上が空から暗色へ」
  と出た時点で写り込みを疑えた。**ハッシュが変わったら、まず画像そのものを見る。**
- **GPU 時間の絶対値は環境に強く依存する。異なる時刻の測定値を比較しない。** この調査中、同じコードで
  13.5ms と 26ms（約 2 倍）を行き来した。私は一度「play.ts が原因」と結論しかけたが、

  「HEAD 25.3/26.9/25.9、現行 27.2/26.3/26.2 = 差なし」と確定した。
  性能を比較するときは **同一セッション内の交互測定**にする。
- 神田さん自身の Chrome が長時間動いている（別プロセス）。これも GPU 時間に効く。勝手に終了させない。

- 環境光: LUT の cos 重み半球積分（reduce compute）。**4 方向サンプルの平均は不可**——
  西の 1 サンプルが太陽周りの輝きを拾い、地面全体が黄色に飽和した（実測）。
- 法線と日向/日陰: 高さテクスチャから段ごとに rgba16float 1 枚（r,g = 法線 xz、b = 太陽可視度）に焼く。
  画素側は 1 タップ。双三次法線 5.7ms・影の行進 5.3ms が消えて **GPU 11.3ms**。焼きは 47ms（1 回）。
  `rg16float` / `r8unorm` は storage 書き込み非対応（検証エラーで判明）。
- 太陽が動く運用にするなら、この 3 つの焼き直しが要る（数十 ms）。

**★教訓**
- **斜め光では法線 1° の誤差が明るさ 30% の縞になる。** 中距離段（1.6m テクセル）の双線形補間は勾配が
  区分定数で、太陽 3.5° だと横縞として全面に出た。太陽を 25° にすると消える＝法線精度の問題と切り分け。
  双三次（B スプライン）で C1 連続にして解消。
- **影の行進は畦（幅 1.6m）を跨ぎ越すと歯状にアリアスする。** 最初の 2m は 0.25m 刻み。
- 起点の高さ（数式）とテクスチャの高さの数 cm の差は、低い太陽だと 1m 先まで偽の影になる。
  起点での差を光線側に足して打ち消す（shadow acne 対策）。

### 段階3: 田んぼと水面（完了・commit 済み）

**[DECISION] 水面メッシュは正本（WGSL）から compute で区画の形を読み戻して CPU が組む**
- `cellQuery`: 格子索引ごとに「合併の左端かつ田んぼ」なら水面高さと 9×3 の格子点（世界 xz）を返す。
  線は u↔v が互いに依存するので 3 回の不動点反復で交点を落ち着かせる。361 区画・12,452 三角形。
- 小川は `riverQuery`（中心線）から半幅 3.2m の帯（水面 2.6m より広く、土手の下に隠す）。
- 水面の縁は畦の中心線まで伸ばす。畦の頂（基準面 +0.42）は水面（基準面 ±0.2）より高いので隠れる。

**[DECISION] 遠くの畦は幾何でなく「焼いた畦距離」で保つ**
- 畦（幅 1.6m・高さ 0.4m）は遠くではメッシュ間隔（400m 先で 5m）より細く、幾何では表せない。
  足元に応じて広げる方式は上限 3 倍まで（それ以上は区画の内部まで持ち上がり、水面が地形に潜って
  **bird 視点で水が 1 画素も出なかった**。平均輝度が水なしと同一という数値で発覚）。
- 足元 1.5〜3m で畦・道の幾何は消し、代わりに焼いた rgba16float の a に「畦・道の中心線までの距離」を
  入れ、水面シェーダがその線上（< 0.6m）を discard する。どの距離でも区画の網目が残る。

**水面の見え方**
- 空 LUT の映り込み（Fresnel, F0=0.02）＋太陽の円盤の鏡像（畦の影の中では消える）＋濁った浅い水底
  （濡れた泥 0.12・深さ 0.12m の吸収・濁りの散乱）。上から見ると暗い鏡、かすめて見ると空と夕日。
- さざ波は正弦 4 波の和。**画素の足元（かすめる視線では奥行きに伸びる）より短い波は落とす**。
  落とさないと画素より細かい波がモアレになる（実測）。

**[DECISION] 太陽の映り込み位置の機械検証**（指示の落とし穴への対応）
- 平らな水面なら太陽の鏡像方向（sunDir の y を反転）に最も明るい点が出る。ページ側で予測画素と、
  地平線より下で最も明るい領域の重心を比べ、ずれ < 2° を要求。実測 **0.05°**。
- verify は水面視点をもう 1 枚、太陽方位 +8° で撮り直し、予測 Δx −98px に対し観測 Δx −89px を確認。
  「それらしい絵だが物理的に間違っている」状態を毎回機械で弾く。

**★注意（座標系）**: この世界は x=東・z=北・y=上と呼んでいるが、右手系ではこの並びは実地図の鏡像
（北を向くと東が左に見える。方位は左回りに増える）。太陽・視点・映り込みの計算はすべてこの系で
一貫しており、検証も通っている。**実地図と比べる用途が出たら x を反転する**。それまでは触らない。
